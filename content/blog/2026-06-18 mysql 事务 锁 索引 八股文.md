## 一、先把核心概念讲清楚

MySQL InnoDB 默认常见的隔离级别是 **RR（Repeatable Read）**。在这个级别下，普通 `SELECT` 通常走 **快照读**，通过 MVCC 和 Read View 读取可见版本，所以不会看到其他事务正在修改但还未提交的数据。

这样做的好处是：

- 避免脏读
- 避免大部分不可重复读问题
- 让普通查询保持更好的并发性能

但它不是“强一致读”。如果你想拿到最新数据并加锁，就要用 **当前读**。

## 二、快照读 vs 当前读

### 1. 快照读

普通的 `SELECT` 属于快照读，读取的是事务可见版本，不会主动加锁。

### 2. 当前读

像下面这些操作都属于当前读：

- `SELECT ... FOR UPDATE`
- `UPDATE`
- `DELETE`

它们会读取最新可见数据，并对命中的记录加锁，确保后续修改安全。

## 三、锁等待和死锁

**锁等待**：一个事务想改某条记录，但这条记录已经被别的事务锁住了，只能等对方释放。

**死锁**：多个事务互相持有对方需要的锁，形成循环等待，最后 InnoDB 会主动挑一个事务回滚。

面试里可以直接说：

> 锁等待是“等别人放锁”，死锁是“大家互相等，谁也不放”。

## 四、索引决定锁的范围

锁的范围和执行计划强相关，重点看有没有命中合适索引。

### 1. 唯一索引 + 等值条件

通常只锁一条记录，锁范围最小。

### 2. 普通索引 + 范围查询

可能锁住扫描范围，尤其在 RR 下更容易出现 next-key lock。

### 3. 没有合适索引

可能退化成全表扫描，锁住更多无关记录，并发一高，RT 很容易飙升。

所以不是“有索引就行”，而是 **必须命中合适索引**。

## 五、生产上怎么做

1. `UPDATE` / `DELETE` / `SELECT FOR UPDATE` 上线前先看 `EXPLAIN`
2. 重点关注是否出现 `type=ALL`
3. 控制扫描行数，避免大事务
4. 范围更新尽量拆批处理
5. 必要时用 `force index`，但要先确认执行计划真的更合理
6. 事务尽量短，访问顺序尽量一致，减少死锁概率

## 六、面试时可以这样回答

MySQL InnoDB 的并发控制主要靠 **MVCC + 锁**。普通 `SELECT` 是快照读，通过 Read View 读取事务可见版本，不加锁，所以不会阻塞别的写操作。

而 `UPDATE`、`DELETE`、`SELECT FOR UPDATE` 属于当前读，需要读取最新数据并加锁，保证修改的安全性。在 RR 隔离级别下，普通 `SELECT` 通常复用同一个 Read View，所以同一事务里可能一直看到旧值，但当前读仍然会看到最新版本。

锁的范围和索引访问路径有关。唯一索引等值查询通常只锁一条记录，范围查询或普通索引可能锁住更大的范围；如果没有合适索引，就可能扫描和锁住更多记录。

如果两个事务更新同一行，就会出现锁等待；如果多个事务互相等待对方持有的锁，就会形成死锁。工程上要缩短事务、保证访问顺序一致、让 SQL 命中索引，并在应用层做好重试和幂等。

## 七、最后的总结

MySQL 八股文最值得记住的不是术语本身，而是这条主线：

**隔离级别决定可见性，MVCC 负责快照读，锁负责当前读，索引决定锁范围。**

把这条线讲顺，面试基本就稳了。
